# Lakehouse RT Demo

A Databricks App that compares DBSQL Serverless and Lakehouse//RT on one copy of the data,
then puts Lakehouse//RT under scaled dashboard load.

- **Architecture**: what is deployed and how each number is measured.
- **Head to head**: the same six-widget dashboard, loaded on both warehouses at the same moment, with client and engine latency.
- **Scaled load**: 1 to 3,000 simulated dashboard users on the Lakehouse//RT warehouse, with live QPS and engine p50/p95.

The data is three synthetic gold tables generated by one job. There is no pipeline.

```
Browser
  -> Databricks App "lakehouse-rt-demo" (Streamlit, LARGE)
       -> Statement Execution API
            -> DBSQL Serverless warehouse   (head to head)
            -> Lakehouse//RT warehouse      (head to head + scaled load)
                 -> gold_dispute_case_fact          18M rows, clustered (merchant_id, chargeback_filing_date)
                 -> gold_dispute_event_stream       18M rows, clustered (merchant_id)
                 -> gold_merchant_dispute_monthly   ~560K rows, clustered (merchant_id)
```

## Prerequisites

- A Unity Catalog catalog you can create a schema in.
- A DBSQL Serverless warehouse (PRO) and a Lakehouse//RT warehouse. Give them the same size for a fair head to head. For scaled load, set the RT warehouse's autoscale max DBU (for example Small with max 96 DBU/h).
- Databricks CLI with a profile for the workspace.

## Deploy

1. Set the variables once for the `dev` target. Create `.databricks/bundle/dev/variable-overrides.json` (it is gitignored):

   ```json
   {
     "catalog": "<catalog>",
     "schema": "lakehouse_rt_demo",
     "dbsql_warehouse_id": "<dbsql warehouse id>",
     "rt_warehouse_id": "<lakehouse rt warehouse id>"
   }
   ```

2. Deploy: `databricks bundle deploy -p <profile>`
3. Generate the data and grant the app read access (about 5 to 10 minutes): `databricks bundle run generate_data -p <profile>`
4. Start the app: `databricks bundle run lakehouse_rt_demo -p <profile>`
5. Before each demo, press **Pre-warm** in the app (top right), about a minute ahead.

## Warehouse controls

The app stays live without keeping compute on. The top right of every page shows both warehouses' state and two buttons:

- **Pre-warm** starts both warehouses, waits for RUNNING and fills their disk cache with the head-to-head queries, so the first click is not a cold start.
- **Turn off** stops both warehouses now (and any Scaled load run). It also ends anyone else's queries on them.

A watchdog inside the app (`warehouse_keeper.py`) does the work:

1. While the demo is in use (a click within the idle window, or a Scaled load run), it runs `SELECT 1` on running warehouses every 3 minutes so their own auto-stop does not fire mid-demo.
2. After `WAREHOUSE_IDLE_STOP_MINUTES` (default 20) without a click, it stops each running warehouse, unless someone other than the app ran a query on it in that window. These can be shared warehouses, and their own auto-stop covers that case.
3. Checking state is a control-plane call, not a query, so watching never keeps a warehouse awake. Opening a page starts nothing; only Pre-warm, Run and Start do.

Change the limits in `resources/app.yml` (`WAREHOUSE_IDLE_STOP_MINUTES`, `WAREHOUSE_KEEPALIVE_SECONDS`) and redeploy. `scripts/warmup.sh` still works from a laptop.

The data job writes data that ends on the day it runs. The app anchors every time window on the newest date in the data, so the widgets stay populated weeks later. Rerun the job to refresh the dates.

## Demo flow

1. **Architecture**: walk the five bands top to bottom.
2. **Head to head**: press "Show dashboard" twice, then "Run Dashboard". Both panels count up live and freeze on their client time. Engine time and the speed-up appear below. A green check confirms both engines returned identical values.
3. **Scaled load**: select 1,000 users and press Start. Within about 15 s it shows ~400 q/s with engine p50 in the tens of milliseconds and every dashboard live. Stop keeps the numbers on screen.
4. Optional: select 2,000 users to show where one warehouse stops scaling. Engine time rises toward a second.

## How load is generated (Scaled load)

1. Each simulated user is one dashboard with 4 widget queries scoped to its own merchant. Merchants are spread across all 40,000 ids.
2. Each dashboard refreshes every 10 s. Start times are spread evenly across those 10 s, and a scheduler fires due refreshes every 50 ms.
3. **Open loop.** Queries go out on a clock and do not wait for earlier ones. The offered rate is fixed by the user count: users x 4 / 10 s. 1,000 users offer 400 q/s, 2,000 offer 800 and 3,000 offer 1,200.
4. Each statement carries a unique `/* nocache */` comment and returns INLINE JSON with a 30 s wait.
5. One asyncio loop drives 14 HTTP/2 connections, about 90 requests each, because one HTTP/2 connection allows only 100 concurrent streams. Beyond 1,200 in flight, a query is counted as **dropped**, which means the app could not keep up.
6. `perf/rt_scale_job.py` (job `load_test`) runs the same workload from a serverless job with 8 processes. If the job reaches a higher rate than the app at the same user count, the app is the bottleneck.

## How the metrics are captured

| Tile | What it measures | How |
|---|---|---|
| QPS | Successful queries per second | Completions in the trailing 15 s window divided by the elapsed span. The footer shows offered q/s, in flight, errors and drops. |
| client ms | What a dashboard user waits | The app's own clock from send to answer: network, front door, any queue, engine |
| P50 / P95 | Time inside the warehouse | Query history API every second on its own connection. Only `is_final` FINISHED rows, each query counted once. The window ends 3 s in the past because the newest rows are still provisional. |

On Lakehouse//RT, the history `duration` excludes admission wait. The gap between client and engine time is time spent outside the engine.

Two numbers are not in the UI. **Cores busy** = q/s x executor task time (`task_total_time_ms` from query history with metrics). **DBU/h** comes from the warehouse monitoring page or `system.billing.usage`, which lags a few hours.

## What we measured (2026-11-12, Small Lakehouse//RT, autoscale up to 96 DBU/h)

| Users | Offered q/s | Achieved | Engine p50 | Notes |
|---|---|---|---|---|
| 1,000 | 400 | 400 | 22 to 26 ms | 0 errors, ~1.3 to 2.5 executor cores busy |
| 2,000 | 800 | ~782 | ~1.2 s | ~2% HTTP 503, ~5 executor cores busy |
| 2,000 on Medium | 800 | ~786 | ~470 ms, swinging 70 ms to 1.3 s | better, not fixed |

## Learnings

**Load generation**
1. A burst that queues everything at once measures how fast a backlog drains, not throughput. Use an open loop.
2. Threads get slower as they are added (GIL plus TLS). Use asyncio with HTTP/2, and a pool of connections: one connection caps the app at 100 in flight.
3. To know whether the app is the limit, run the same workload from a second generator and compare.

**Measurement**
1. Query history needs care at high q/s: read a few seconds behind, gate on `is_final`, and give the sampler its own connection.
2. Report client and engine latency separately. The difference shows where the time goes.
3. Hold each step at least 3 minutes. Lakehouse//RT needs time to scale, and shorter steps understate capacity.

**Lakehouse//RT scaling**
1. Autoscaling adds executors, 3 DBU/h each. A Small with autoscale multiplier 8 runs 4 to 32 executors (12 to 96 DBU/h).
2. For light lookups the limit is per warehouse, not executor CPU or the DBU cap. At 800 q/s each query needed ~6 ms of executor work while engine time hit ~1.2 s.
3. For more throughput on light queries, add warehouses. Raising the DBU max helps heavier queries that need more executor work.

## Data collection

To improve users' experience and this asset's quality, the app reports a usage event when a page is opened. This information is captured for product improvement only, not for marketing purposes, and doesn't contain PII: the email of Databricks users is hashed, and nobody else's is sent. By using this asset, you consent to this data collection. If you wish to disable it, set the environment variable `DBDEMOS_TRACKER_DISABLED=1` (e.g. add `- name: DBDEMOS_TRACKER_DISABLED` with `value: "1"` under `config.env` in `resources/app.yml`, then redeploy).

